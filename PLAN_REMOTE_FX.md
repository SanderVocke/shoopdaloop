# Remote Carla FX on the Native Backend

Run Carla chains on the desktop that runs the ShoopDaLoop UI while the production Native session host owns the audio clock, routing, and loop media. Use the existing buffered processor to schedule wet returns from a duplicated UDP stream. Deliver a deterministic transport fixture, stereo Carla over two isolated network endpoints, wider and concurrent chains, and setup and inspection in Host Manager.

Base the implementation on `feat/backend-replacement`, inspected at `55bd4475a8ce5e5809f0c57ce132ce61ed08e56e`. Scope covers the independent Native session host, native desktop UI, desktop FX service, and Host Manager. FreeRTOS, FPGA, and other embedded integrations are excluded. [Native backend and launch roles](src/rust/shoopdaloop/README.md#native-roles-and-delivery) · [Carla hosting contract](docs/native_session_recovery/track-processors.md#carla-development-builds) · [Planning instructions](.agents/prompts/write_plan.md)

## Immutable acceptance criteria

| ID | Required result |
| --- | --- |
| A1 Native workflow | A production Native session host sends a stereo track over IP to a separate desktop FX service and receives real Carla output. An automated run of the normal track FX control opens the editor in the service's desktop session. Remote is an explicit Native host startup mode. Existing local Carla modes and session files continue to work. |
| A2 Timing and realtime | Negotiated quantum, batch size, and slack yield the declared source-to-wet delay for every successful batch. Audio channels and timed MIDI remain aligned. The render callback uses bounded prepared work with zero allocations, deallocations, locks, waits, or socket calls. Early, late, duplicate, malformed, and retired-generation traffic cannot change the release schedule or publish against another source frame. |
| A3 Loss, status, and recovery | Each datagram is sent twice at the default setting and each input batch runs at most once. Missing batches follow the existing wet silence and MIDI recovery policy. Lost network traffic and service failures leave unrelated tracks and session operation running. The UI shows confirmed activity, lifecycle, failure, and useful counters. Recovery restores the last confirmed project and desired activity under a fresh stream identity. |
| A4 State and capture | Saves contain confirmed Carla state and existing processor identities. A session can be restored with compatible local or remote Carla. Wet recording and dry-to-wet rerecord preserve source alignment. A failed private restore or a missing required wet return preserves the committed session or take and reports the failure. |
| A5 Width and capacity | The wire format negotiates ordered input and output widths independently. Production verification covers stereo, Patchbay 16x, and at least two concurrently active remote chains. Prepared render storage, receive windows, network traffic, and active and candidate capacity stay within declared limits. Unsupported shapes and exhausted capacity produce explicit refusals. |
| A6 Operational setup | Host Manager can launch and rediscover a local FX service, inspect an explicitly entered service address, and use that endpoint when configuring a Native host. It shows compatibility, available shapes and capacity, and health. The FX service survives closing the manager or UI and can be stopped explicitly. An automated run completes this workflow from extracted release artifacts with the supported Carla component. |
| A7 Delivery evidence | An unattended run provisions two isolated network endpoints, verifies the installed Native workflow and fault recovery, and collects results. Run stereo and wide concurrent Carla workloads for 30 minutes each on clean virtual Ethernet at 48 kHz with a 128-frame driver period and 32-frame graph quantum. Verify at most 12 ms of declared node delay, continued playback, and the expected wet signal before and after each run. Record completion tails, callback load, queue peaks, packet rate, wet misses, and driver xruns. The soak tolerates isolated scheduling misses on the cloud runner and fails if a chain misses more than 1% of its batches or changes generation during the clean run. Link evidence to the final PR head and pass applicable Native CI. |

## Design rules

- Use a prepared `rt_buffered::AsyncTransport` as the render boundary. Reuse the local worker's queue and storage ownership where practical. The current `LocalWorker::process_next` handles one job through completion, so the network worker needs a bounded way to own multiple in-flight jobs and return each slot asynchronously. Keep encoding, sockets, timers, negotiation, and teardown off-render. [Transport contract](src/rust/rt_buffered/src/transport.rs) · [Local worker](src/rust/rt_buffered/src/local.rs#L235)
- Use a versioned TCP control connection and one bidirectional UDP flow per chain. Negotiate sample rate, quantum `Q`, DSP batch length `M`, extra release slack `S`, input and output channel layouts, MIDI limits, datagram ceiling, and copy count before activating a prepared stream. Bind admission to an explicitly configured trusted-LAN endpoint and verify the UDP return address before streaming. Bound every request, queue, receive window, and reservation. Use request IDs for retryable control operations and a fresh stream identity on reconnection. [Trusted-LAN setup precedent](docs/trusted-lan-networking.md) · [UDP usage guidelines](https://www.rfc-editor.org/rfc/rfc8085)
- Send one logical quantum at a time using specified-endian planar float32 PCM and bounded MIDI with frame offsets. Carry stream identity, generation, sequence, and fragment position. Return the original quantum identity and reconstruct the original `BatchTag` at the looper. Use a 1,200-byte initial UDP payload ceiling and fragment larger quanta at the application layer. Deduplicate per fragment, publish only complete channel sets, and bound reordering and stale work. Render complete DSP batches once in source order. If a required input quantum expires, skip that batch and apply the existing Carla discontinuity cleanup before processing the next one. A missing return expires at the looper's scheduled release. [Carla batch processing](src/rust/shoop_carla/src/buffered.rs#L196)
- The looper's source clock drives Carla. Group `M` wire quanta into each DSP batch and let `BufferedProcessor` own the scheduled release at `(M + S) × Q` frames. Report host I/O buffering and any known intrinsic DSP latency separately. Reprepare the node when timing changes. Test burst dispatch from callbacks containing several graph ticks. Use `Q=32`, `M=4`, `S=8` as the first 48 kHz, 128-frame-period measurement point. [Buffered timing](src/rust/rt_buffered/README.md#timing) · [Native Carla preparation](src/rust/shoop_rt_host_native/src/carla.rs#L94)
- Keep placement at Native host startup and keep Carla kind and project state in the existing session model. Prepare active and private candidate banks within explicit budgets at both ends, account for source-history storage, and fence slot reuse, controls, and checkpoints by owner and generation. Send bounded confirmed state over TCP. Apply session replacement only after the remote candidate validates, and reclaim reservations on abort, disconnect, and lease expiry. Use the existing worker capture path and wet release identity. [Hosted control contract](src/rust/shoop_rt_engine/src/endpoint.rs#L163) · [Worker capture release](src/rust/shoop_rt_engine/src/processors.rs#L749)
- Run the FX service as a detached native role launched from the Carla-enabled companion installation. Reuse Carla's DSP and editor ownership on the desktop, with editor dispatch on its main thread. Keep status current through control heartbeats even while idle. Report confirmed active state separately from lifecycle and distinguish a disconnected service, worker failure, and late or missing wet output. The manager can inspect services without owning an audio stream. [Carla service](src/rust/shoop_carla/src/service.rs) · [Host Manager](src/rust/shoopdaloop/README.md#host-manager)
- Use a paced Native Dummy driver, generated source audio and MIDI, a repository-pinned Carla component, and Xvfb for the automated desktop. Put the looper and desktop service in separate Linux network namespaces connected by virtual Ethernet for the installed workflow and timing runs. Use disjoint CPU affinities when the runner has at least four CPUs. Use a seeded userspace datagram relay for fault cases. Scope timing claims to the recorded runner, driver, plugin load, and virtual link. [Carla CI fixture](.github/workflows/build_and_test.yml#L240) · [Installed package probes](scripts/smoke_engine_package.py)

## Stage 4 Qualify Native capacity and latency

Depends on Stage 3. Establish the supported profiles before exposing the settings as defaults.

- [x] Script a stereo sweep at 48 kHz on the Linux virtual Ethernet runner under concurrent package-test load. In five-second runs with a 32-frame quantum, periods of 64, 128, 128, and 256 frames gave 192, 384, 576, and 768 frames of node buffering, with 26, 2, 0, and 2 total wet misses across the two chains. The 576-frame case processed 237,824 frames, reached a peak worker completion age of 256 frames and a peak queue of three batches, and saw about 12,500 datagrams/s at the service. ## Stage 6 Validate the installed workflow and complete review

Depends on Stages 2–5. Run the full acceptance workflow on the final candidate.

An initial installed run at 12 ms reported a stereo wet miss after 19.4 seconds on the Cloud VM. The desktop media worker now wakes on UDP arrival and calls the existing Carla batch processor directly. This removes the extra desktop queue and worker handoff and preserves the transport and release schedule. The sustained gate records guest scheduling effects and checks continued processing under the acceptance criteria above.

CodeQL flagged the initial TCP decoder. The updated decoder rejects positional records, unknown fields, and trailing JSON. Regression tests cover those refusals and an inspection response with counters for every advertised slot. The UDP media format and timing are unchanged. [Control wire schema](docs/design/remote-fx-wire.md#control)

A CI restart reached new stream generations while wet output stayed silent. The client now consumes the pending socket and its notification together so a reconnect cannot discard the replacement socket. A fresh Carla instance keeps its restored activation through its first batch. The restart fixture reports the service-side stream counters when a check fails. [Client reconnect](src/rust/shoop_remote_fx/src/client.rs) · [Failure diagnostics](scripts/verify_remote_fx.py)
