# FPGA architecture

## Purpose

Explore the feasibility of an FPGA implementation of ShoopDaLoop's real-time
audio backend. Early prototypes will help estimate resource usage, throughput,
and timing, and guide subsequent architectural decisions.

Hard real-time behaviour is the eventual objective; the initial architecture
does not establish that guarantee.

## Overall decomposition

```text
Audio graph                       Loop commands / timing dependencies
    |                                          |
    v                                          v
Compiler                              Transition processor
    | program                             | settled decisions
    +-----------------> State processor <-+
                             | jobs
                             v
                        Job processor
                             |
                             v
                     Audio / external memory
```

The execution hardware does not interpret graph topology. The compiler
translates the graph into a program that coordinates state updates and audio
work.

## Compiler

The compiler maps graph nodes and their dependencies into a scheduled program
for the state processor.

Initially, programs may be handwritten or generated by simple scripts. A
complete graph compiler is not required to explore the execution architecture.

## Transition processor

The transition processor owns logical loop timing, scheduled actions, and
transition propagation between loops. Its dependency order follows timing and
synchronization relationships, independently of audio routing. Future composite
loop handling belongs here; it is not part of the initial prototype.

At a processing boundary it resolves commands and timing events into settled
loop decisions for the state processor. It advances logical clocks and produces
wrap events at the following boundary. Preparing a recording can fail, so state
preparation must be able to return feedback before a transition is committed.

The Rust hardware model now uses prepared logical loop state, generation-checked
request slots, canonical timing components, and preview/commit/finish transactions.
Preflight feedback can replace a candidate without publishing state or consuming
source delays twice. Signal bindings export settled decisions to the state
processor; the transition processor alone advances logical clocks. Composite
kinds/timeline references are reserved but explicitly unsupported in this first
primitive-only version. Serialized boundary traces are checked against the native
resolver. RTL and packed memory/interface layouts remain to be implemented.

## State processor

The state processor consumes settled loop decisions and executes operations on
node state and metadata: gains, ramps, media-view handles, and frame ranges. It
uses logical playback positions supplied by the transition processor and emits
jobs describing work for the job processor. It owns physical capture preparation
and publication, with feedback to transition processing when needed.

The initial Rust reference uses single-issue instructions that process whole
nodes against their live state and emit jobs. Programs remain unchanged across
loop mode and parameter changes; structural graph changes produce a new program.
Scheduled actions, transition propagation, and logical clocks are outside this
processor. A smaller hardware-like instruction set can be derived in a later
step. VLIW with
lock-step issue slots is a possible later extension, allowing multiple
independent metadata operations per cycle. The instruction set and degree of
parallelism remain open.

## Job processor

The job processor consumes an ordered stream of jobs and performs sample
processing and the bulk, potentially all, of external-memory access.

Jobs may describe reading a media range, writing captured audio, applying gain
or ramps, mixing, and delivering output. Jobs can refer to intermediate results
produced by earlier jobs.

The state processor can work with media views and ranges; the job processor
resolves these into the underlying stored chunks. Exact job formats and
execution strategies will be developed incrementally.

## Storage model

Audio is stored in chunks identified by IDs. Media views map logical frame
ranges onto stored audio.

The processing quantum is initially assumed to be 32 frames. Storage chunks may
have the same size or contain multiple quanta.

Complete sample storage and media indexes reside in external RAM. On-chip
memory holds active processor state, programs, queues, and bounded working
buffers. The architecture does not require the full session's chunk IDs to fit
in BRAM.

## Numerical representation

Use 32-bit fixed-point audio as the initial direction. Gain formats,
intermediate precision, rounding, and saturation remain undecided.

## Toolchain

Use SystemVerilog with the open-source OSS CAD Suite: Yosys for synthesis,
nextpnr for placement and routing, and Verilator for simulation.

Use ECP5 as an initial reference target for resource and timing estimates,
without committing the eventual implementation to that family.

## Initial exploration

Start with state execution and job generation. A simulated job processor can
model execution delays and memory behaviour before sample processing is
implemented.

Develop these subsystems incrementally, using measurements to decide where
greater complexity is justified.

## Scope

Audio only. **No MIDI in the architecture or initial prototypes.**

## Rust functional reference

The `rt_fpga_reference` crate provides a readable single-issue software model of
this decomposition. It also has an experimental `fpga-reference` native renderer
for app-connected comparisons. See `src/rust/rt_fpga_reference/README.md` for the
supported subset, execution example, and boundaries of the existing app adapter.

The `rt_fpga_testbench` tool and Python helpers exchange versioned JSON values
validated against a schema generated from Rust. Reference traces record ordered
jobs and architectural state after each quantum, providing a comparison boundary
for a future cocotb/SystemVerilog testbench without fixing internal hardware
layout or cycle counts. See `scripts/fpga_testbench/README.md`.

The Rust reference uses an elastic contiguous sample-slot arena, dynamic per-view
chunk-ID tables, and deterministic reuse of released slots. It has optional chunk
limits for hardware comparisons and capacity hints for host preparation, with no
BRAM-cache simulation. Media snapshots and control actions extend the audio trace
boundary to capture, playback, reclamation, and allocation failure. Native app
media storage remains behind its existing resource adapter.

## State processor RTL prototype

`fpga/state_processor` contains a multicycle SystemVerilog state processor with
synchronous program/state memories and a finite job FIFO. It implements the
standalone reference's six node instructions. Its README specifies the packed
instruction/state/job ABI, configuration protocol, and synthesis commands.
Lint, synthesis checks, and a cocotb/Verilator behavioral comparison against
versioned Rust traces are available. The bench compares ordered jobs, complete
state, and status per quantum, with separate hardware protocol checks. Transition
and job processors are outside this RTL prototype.

## BRAM job processor milestone

`fpga/job_processor` adds synthesizable Input/Silence/Gain/Mix/Output execution
and an `audio_pipeline` wrapper connected to the state processor's FIFO. BRAM
holds reusable quantum scratch and I/O buffers. A shared multiplier and iterative
ramp initialization preserve the Rust fixed-point semantics. The cocotb bench
compares full state, buffer readiness, intermediate/output samples, and FIFO
effects against traces from both actual Rust processors. See that directory's
README for interface, coverage, cycle counts, and ECP5 synthesis results. Media
playback/capture and external-memory access remain deferred.
