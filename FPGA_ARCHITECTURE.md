# FPGA architecture

## Purpose

Explore the feasibility of an FPGA implementation of ShoopDaLoop's real-time
audio backend. Early prototypes will help estimate resource usage, throughput,
and timing, and guide subsequent architectural decisions.

Hard real-time behaviour is the eventual objective; the initial architecture
does not establish that guarantee.

## Overall decomposition

```text
Audio graph
    |
    v
Compiler
    | program
    v
State processor
    | jobs
    v
Job processor
    |
    v
Audio / external memory
```

The execution hardware does not interpret graph topology. The compiler
translates the graph into a program that coordinates state updates and audio
work.

## Compiler

The compiler maps graph nodes and their dependencies into a scheduled program
for the state processor.

Initially, programs may be handwritten or generated by simple scripts. A
complete graph compiler is not required to explore the execution architecture.

## State processor

The state processor executes operations on node state and metadata: playback
positions, gains, ramps, media-view handles, and frame ranges. It emits jobs
describing work for the job processor.

The first implementation should use a simple single-issue processor. VLIW with
lock-step issue slots is a possible later extension, allowing multiple
independent metadata operations per cycle. The instruction set and degree of
parallelism remain open.

## Job processor

The job processor consumes an ordered stream of jobs and performs sample
processing and the bulk, potentially all, of external-memory access.

Jobs may describe reading a media range, writing captured audio, applying gain
or ramps, mixing, and delivering output. Jobs can refer to intermediate results
produced by earlier jobs.

The state processor can work with media views and ranges; the job processor
resolves these into the underlying stored chunks. Exact job formats and
execution strategies will be developed incrementally.

## Storage model

Audio is stored in chunks identified by IDs. Media views map logical frame
ranges onto stored audio.

The processing quantum is initially assumed to be 32 frames. Storage chunks may
have the same size or contain multiple quanta.

Complete sample storage and media indexes reside in external RAM. On-chip
memory holds active processor state, programs, queues, and bounded working
buffers. The architecture does not require the full session's chunk IDs to fit
in BRAM.

## Numerical representation

Use 32-bit fixed-point audio as the initial direction. Gain formats,
intermediate precision, rounding, and saturation remain undecided.

## Toolchain

Use SystemVerilog with the open-source OSS CAD Suite: Yosys for synthesis,
nextpnr for placement and routing, and Verilator for simulation.

Use ECP5 as an initial reference target for resource and timing estimates,
without committing the eventual implementation to that family.

## Initial exploration

Start with state execution and job generation. A simulated job processor can
model execution delays and memory behaviour before sample processing is
implemented.

Develop the state processor, job processor, and compiler incrementally, using
measurements to decide where greater complexity is justified.

## Scope

Audio only. **No MIDI in the architecture or initial prototypes.**

## Rust functional reference

The `rt_fpga_reference` crate provides a readable single-issue software model of
this decomposition. It also has an experimental `fpga-reference` native renderer
for app-connected comparisons. See `src/rust/rt_fpga_reference/README.md` for the
supported subset, execution example, and boundaries of the existing app adapter.
