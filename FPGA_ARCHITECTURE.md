# FPGA architecture

## Purpose

Explore the feasibility of an FPGA implementation of ShoopDaLoop's real-time
audio backend. Early prototypes will help estimate resource usage, throughput,
and timing, and guide subsequent architectural decisions.

Hard real-time behaviour is the eventual objective; the initial architecture
does not establish that guarantee.

## Overall decomposition

```text
Audio graph                       Loop commands / timing dependencies
    |                                          |
    v                                          v
Compiler                              Transition processor
    | program                             | settled decisions
    +-----------------> State processor <-+
                             | jobs
                             v
                        Job processor
                             |
                             v
                       Media frontend
                             |
                             v
                        Chunk memory
                             |
                             v
                     Audio / external memory
```

The execution hardware does not interpret graph topology. The compiler
translates the graph into a program that coordinates state updates and audio
work.

## Compiler

The compiler maps graph nodes and their dependencies into a scheduled program
for the state processor.

Initially, programs may be handwritten or generated by simple scripts. A
complete graph compiler is not required to explore the execution architecture.

## Transition processor

The transition processor owns logical loop timing, scheduled actions, and
transition propagation between loops. Its dependency order follows timing and
synchronization relationships, independently of audio routing. Future composite
loop handling belongs here; it is not part of the initial prototype.

At a processing boundary it resolves commands and timing events into settled
loop records for the state processor, executes state/jobs/media and advances
logical clocks on success. Preparing a recording is ordinary internal work.
Required allocation/processing failures latch an engine fault and silence output
until reset/reload. There is no host preflight, resource-refusal feedback or retry.
[SIMPLIFY.md](SIMPLIFY.md) defines the processing/publication contract.

The Rust model and SystemVerilog transition controller use one loop/request/event
bank, generation-checked requests and canonical timing components. Prepared
follower links, pending-request lists and priority masks preserve canonical order
without speculative table copies. State instructions read stable settled records
through a shared RAM port; only the transition processor advances logical clocks.
Composites/timelines remain reserved. Successful musical cases are checked against
the independent native resolver and exact Rust/RTL traces.

`fpga/loop_pipeline` coordinates settlement, internal state/job/media execution and
clock advancement under one public run/completion handshake. Node state retains
view handles and ramps without duplicating logical modes/clocks. `BeginCapture`
creates/reuses a recording view internally. Media ownership, reference counting,
shared ranges, bounds checks and AXI backpressure/coherence remain necessary.
Failed output is suppressed even after partial sample work; partial state is
available only for diagnostics. Rust additionally silences an entire multi-quantum
host block when any quantum fails. An app/ARM transport must use that same policy.

## State processor

The state processor consumes settled loop decisions and executes operations on
node state and metadata: gains, ramps, media-view handles, and ranges in chunk counts. It
reads logical playback positions from the settled loop table and emits
jobs describing work for the job processor. It emits internal recording preparation and sample jobs; required failures fault
the coordinator.

The initial Rust reference uses single-issue instructions that process whole
nodes against their live state and emit jobs. Programs remain unchanged across
loop mode and parameter changes; structural graph changes produce a new program.
Scheduled actions, transition propagation, and logical clocks are outside this
processor. A smaller hardware-like instruction set can be derived in a later
step. VLIW with
lock-step issue slots is a possible later extension, allowing multiple
independent metadata operations per cycle. The instruction set and degree of
parallelism remain open.

## Job processor

The job processor consumes an ordered stream of jobs and performs sample
processing. A media frontend resolves views/ranges into chunk spans, and a
separate chunk-memory subsystem handles buffered sample access and external
transfers. Arithmetic scratch remains with the job processor.

State enqueue events also feed an advisory read-intent FIFO and a separate
resolver using existing media metadata. Chunk memory owns coherence across
intervening writes; demand jobs preserve their execution-time lookup. See
[early prefetch](FPGA_CHUNK_PREFETCH.md).

Jobs may describe reading a media range, writing captured audio, applying gain
or ramps, mixing, and delivering output. Jobs can refer to intermediate results
produced by earlier jobs.

The state processor can work with media views and ranges; the media frontend
resolves these into the underlying stored chunks. Exact job formats and
execution strategies will be developed incrementally.

## Chunk memory

Chunk memory exposes read/write spans, advisory prefetch, fence and retirement.
RTL owns bounded read/write BRAM pools, a shared coherence directory and a chunk
transfer scheduler. Writes complete when buffered and visible, with asynchronous
DDR writeback; fences and retirement account for outstanding transfers. The Rust
implementation retains an elastic arena and immediate completion. Both standalone
and full-loop tests compare logical results; separate protocol tests exercise
backpressure, forwarding, reuse and late faults. See
[the design](FPGA_CHUNK_MEMORY.md) and [implementation](fpga/chunk_memory/README.md).
The integrated RTL tops use a shared synthesizable AXI master for external
sample and metadata memory. Separate DMA clients alternate at complete AXI burst
boundaries, with one outstanding transaction. Native direct simulation uses an SV
backing store; realistic simulation uses cocotb and a ctypes-wrapped DRAMsim3 model. See
[AXI memory](fpga/axi_memory/README.md).

## Storage model

Audio is stored in chunks identified by IDs. Media views map logical chunk
ranges onto stored audio.

The primary profile uses a 32-sample quantum and 32-sample chunks. Media jobs
address whole chunks, with positions in chunk indices and lengths in chunk counts.

Complete sample storage and media indexes reside in external RAM. On-chip
memory holds active processor state, programs, queues, and bounded working
buffers. The architecture does not require the full session's chunk IDs to fit
in BRAM.

## Numerical representation

Use 32-bit fixed-point audio as the initial direction. Gain formats,
intermediate precision, rounding, and saturation remain undecided.

## Toolchain

Use SystemVerilog with the open-source OSS CAD Suite: Yosys for synthesis,
nextpnr for placement and routing, and Verilator for simulation.

Use ECP5 as an initial reference target for resource and timing estimates,
without committing the eventual implementation to that family.

## Initial exploration

Start with state execution and job generation. A simulated job processor can
model execution delays and memory behaviour before sample processing is
implemented.

Develop these subsystems incrementally, using measurements to decide where
greater complexity is justified.

## Scope

Audio only. **No MIDI in the architecture or initial prototypes.**

## Rust functional reference

The `rt_fpga_reference` crate provides a readable single-issue software model of
this decomposition. It also has an experimental `fpga-reference` native renderer
for app-connected comparisons. See `src/rust/rt_fpga_reference/README.md` for the
supported subset, execution example, and boundaries of the existing app adapter.

The `rt_fpga_testbench` tool and Python helpers exchange versioned JSON values
validated against a schema generated from Rust. Reference traces record ordered
jobs and architectural state after each quantum, providing a comparison boundary
for a future cocotb/SystemVerilog testbench without fixing internal hardware
layout or cycle counts. See `scripts/fpga_testbench/README.md`.

The Rust reference uses an elastic contiguous sample-slot arena, dynamic per-view
chunk-ID tables, and deterministic reuse of released slots. It has optional chunk
limits for hardware comparisons and capacity hints for host preparation, with no
BRAM-cache simulation. Read-only range views share recorded chunks, including
partial boundary chunks; each slot is reusable after its last view releases it.
Media snapshots and control actions extend the audio trace
boundary to capture, playback, reclamation, and allocation failure. The app's
reference backend uses this store behind native resource revisions and snapshot
leases, with fixed-point capture/playback and float conversion for persistence.
It permits callback-time growth; warmed playback uses prepared storage. Retired
recordings reclaim chunks incrementally, while pinned snapshots retain their
published prefixes.

## State processor RTL prototype

`fpga/state_processor` contains a multicycle SystemVerilog state processor with
synchronous program/state memories and a finite job FIFO. It implements the
standalone reference's six node instructions. Its README specifies the packed
instruction/state/job ABI, configuration protocol, and synthesis commands.
Lint, synthesis checks, and a cocotb/Verilator behavioral comparison against
versioned Rust traces are available. The bench compares ordered jobs, complete
state, and status per quantum, with separate hardware protocol checks. This
isolated top keeps transition and job execution separate; `loop_pipeline`
connects all three processors and the media store.

## BRAM job processor milestone

`fpga/job_processor` adds synthesizable Input/Silence/Gain/Mix/Output execution
and an `audio_pipeline` wrapper connected to the state processor's FIFO. BRAM
holds reusable quantum scratch and I/O buffers. A shared multiplier and iterative
ramp initialization preserve the Rust fixed-point semantics. The cocotb bench
compares full state, buffer readiness, intermediate/output samples, and FIFO
effects against traces from both actual Rust processors. See that directory's
README for interface, coverage, cycle counts, and ECP5 synthesis results.

`fpga/media_store` adds a bounded RTL counterpart of the Rust chunk store, including
shared read-only ranges, reference counts and deterministic slot reuse. Compact
descriptors/roots remain on chip; allocated chunk-ID vectors, reference counts and
the reusable-ID stack live in DDR behind bounded persistent caches. Its
`media_audio_pipeline` connects ReadView/Capture jobs to that store and is also
instantiated by the transition-coordinated `loop_pipeline`. Cocotb compares
serial store commands and complete audio quanta against Rust, including sample
bits, ownership, FIFO effects and memory backpressure. Samples and metadata share
the integrated AXI burst endpoint. See [metadata design and capacities](fpga/media_store/DDR_METADATA.md).
Physical DDR controllers and board integration remain future work.
