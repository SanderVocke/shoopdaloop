## Design rules and constraints

- Keep current paths, numbering and independent focused examples. Put unnumbered references outside the chapter sequence; add no competing flat guides.
- Explain a concept at its practical point of use, then link to its main explanation. Disclose safety/ownership restrictions before first use; later sizing/shutdown chapters consolidate rather than first reveal them.
- Distinguish signal routes from planner/decision dependencies and loop sync/action relationships. One render-owned planner settles its domain; consumers borrow decisions and report observations, not mutate a second clock.
- Distinguish command admission, owning completion, scheduled delivery, terminal receipt and domain publication. Copied resource handles do not acquire leases, and pending operation tokens do not own or lock Ready graph candidates.
- Distinguish startup installation, ordinary callback-ingress Commit and staged planner-boundary activation. Graph permits, capture groups and loop-domain transactions have separate authority/ownership; none is general rollback or arbitrary processor construction.
- Use half-open intervals. Callback end is settled by the next nonempty callback, not `finish` or a zero call. Internal intervals do not renew callback-wide admission/recycle/validation/background/recovery/telemetry allowances. There is no arbitrary musical subdivision quota; finite domain structure must establish termination.
- Required `RenderIo` media work is independently counted and capacity/shape/time validated, not throttled by optional background allowances. Finite prepared storage is not a hard deadline guarantee. Diagnostic counters saturate; semantic frame/revision/generation exhaustion does not wrap.
- Keep raw resource/snapshot IDs' same-store precondition distinct from scoped index/cursor validation. Resource revisions, musical take revisions, graph/topology epochs and stage generations are separate identities.
- Keep strict-pre-target MIDI state lookup separate from cleanup/restoration emission, equal-time original packets and arbitrary downstream synthesizer state. Attribute loop renderers/configuration helpers to `shoop_loop_engine`.
- A fault after publication does not undo the cut. Never replay frames or fake `finish`; continuation depends on domain policy. Stopped extraction must retain any cleanup ledger; disconnect is not Stop or device cleanup.
- Use deterministic offline data, finite driving loops and exact sample/event/result assertions. No devices, sleeps, browser dependency or portable performance thresholds in ordinary examples. Keep mechanical helpers small and visibly separate from public APIs.
- Keep construction, owning-return disposal and final destruction off-render. Handle refused payloads, retained results and acquired leases on failure paths as well as success paths. Do not hide ownership in an application framework.
- Use `nix develop --command ...` on this host, with `CARGO_TARGET_DIR=/tmp/rt-runtime-docs-rewrite-target` for example runs. Follow repository editing/style guidance and preserve unrelated work.
- Keep brief milestone notes here, not a second accounting system. Do not run/extend the existing book checker or machine-readable inventory as part of authoring. No automatic documentation checks or CI integration are required.
- The archived review is optional detailed reference, not an active handoff queue. Resolve its chronological contradictions against the final source and actual evidence. Do not refresh baseline JSON or follow old instructions to await later stages, re-audit drafts or obtain separate publication sign-off.
- Missing implementation remains an explicitly documented limitation. Do not create APIs, host/wire recipes, benchmark results or dependency on another implementation stage to make the docs appear complete. Escalate an actual contradiction rather than changing code or silently weakening guarantees.
- Public rustdoc edits are prose-only. Preserve signatures and behavior; if changing a runnable teaching example, run that example in debug/release. Do not create a new script/test/benchmark campaign to validate this documentation plan.
